# 正反方剧本讨论与主理汇报

用于已有大纲、单集或片段的审稿与复核。以作者目标为判断依据；讨论请求只授权审稿与建议，不自动覆盖原稿或启动媒体生成。可挂在 N01／N02／N14，也可独立使用。

## 1. 固定输入和讨论范围

- 登记稿名、版本、文件及本轮覆盖范围。原稿无场号时建立评审用场号／段落锚点，不改原文件；记录短原文，保证能找回依据。
- 读取已有作者意图、受众、类型、时长、人物设定、世界规则和锁定项。缺少这些不先发一串问题：能审的先审；影响结论的缺项标为待确认。没有正文时只审已提供大纲，不编造场次或对白。
- 默认一轮覆盖用户指定片段或一集，重点选影响理解、情绪与人物的争议。未指定重点时据现稿提出审稿重点并推进；不擅自扩审整季。
- 用 [任务与记录模板](../assets/script-review-template.md) 固定输入。审稿过程中稿件更新，保留旧轮并另开新版本，不把两稿意见混为一谈。

## 2. 五个角色的执行约定

主理人统筹，另外四席先只拿同一稿件、作者目标与锁定项，首轮不看其他席意见。各席按下列任务执行，而非扮演带情绪的辩论人格。

| 角色 | 本席任务指令 | 应交付的判断 |
|---|---|---|
| 主理人 | 固定范围、核对引文、归并相同问题；讨论前不预设结论。按作者目标与证据裁决，解释代价，保留未解决分歧。 | 总体判断、保留亮点、关键争议、逐项裁决、修改任务与待决定项 |
| 正方／作品辩护 | 从现稿找有效的冲突、悬念、情绪与结构，解释成立机制和支撑原文；指出改动会损伤什么。回应反方时承认成立的问题，不为所有段落辩护。 | 有依据的优点、保留理由、可成立的替代解释及适用条件 |
| 反方／质询 | 检查因果断裂、信息缺口、规则冲突、节奏失衡、未兑现铺垫；先找可能的原文解释再质询。说明严重性，给出最小修补或需要补充的证据。 | 具体位置、问题机制、反例／条件、建议；允许“没有重大问题” |
| 人物与关系 | 沿“目标→已知信息→选择→代价→关系变化”检查行为；区分有意矛盾与缺少动机，不用刻板性格要求人物永远一致。 | 人物行动链、关系转折、人物弧光、需要保护或补足的节点 |
| 观众体验 | 按首次观看的信息顺序判断是否看懂、期待什么、何时获得回报；区分悬念与困惑。基于目标受众提出感受假设，不冒充真实观众数据。 | 信息与情绪节拍、理解门槛、钩子和兑现、需要试听／试看的假设 |

若当前宿主允许且工具可用，完整五席讨论可由主理人协调四个独立评审代理；各代理只读原稿，在各自记录范围写意见，讨论前不互相提供结论。并发不足可分批，不按角色数量抢占资源。遵循当前宿主的代理授权规则；不因本文件绕过禁止委派的指令。

若没有独立代理，则由同一代理依次完成四个视角，明确标记“多视角自审，意见不具备代理间独立性”；不声称已启动团队或完成独立交叉验证。记录实际执行模式和哪些席位完成；缺席不伪造补齐。

## 3. 每条意见都能回到原稿

每席使用统一意见格式，正向判断同样需要证据：

`意见ID → 位置 → 短原文依据 → 判断 → 对剧情／人物／观众的影响 → 建议与代价 → 不确定项`

- 位置含稿件版本、集／场／段落；意见用 R01-POS01、R01-NEG01 等稳定 ID。主理归并后用 R01-I01 关联各席原意见，不能丢掉反证。
- 判断注明类型：**文本事实／分析推断／创作偏好／待验证假设**。一条意见混合多类时分别标记，不把“我觉得观众会流失”写成事实。
- 问题影响分为：阻断理解或违反锁定规则／显著削弱动机与情绪／可选优化。优点标为保留项，不硬套问题等级；不强制各席凑数量或平均分配赞成与反对。
- 有把握程度附理由，避免伪精确分数。跨集材料未给出时，不能把“本段未出现”直接判成“全剧没有”；外部专业机制尚未核实就保留待核验。
- 找不到引用时回查、降级为假设或撤回；不得为了支持结论补写不存在的台词。引用短而准确，保留用户原文措辞。

## 4. 从独立审稿到讨论与裁决

1. **首轮审稿**：四席分别提交意见，主理人查引文与覆盖范围，归并重复问题。除问题外明确哪些已经成立，不用改。
2. **选关键争议**：只讨论会影响改稿方向的分歧。每项列出“争议命题、支持依据、反对依据、人物视角、观众视角、缺失信息”。无争议的修正直接归入建议，不举行表演式辩论。
3. **交锋**：正方回应最强质询，反方回应最强辩护；人物和观众席检验两种方案的后果。记录哪些判断改变及其依据，不以重复表态当新证据。
4. **主理裁决**：默认一轮交锋；出现新证据或关键分歧仍未解决，可再补一轮。没有新依据就停止循环，记录待验证。裁决用“采纳／部分采纳／不采纳／待验证”，写理由、保留异议、最小修改方向、代价与复核条件。按证据裁决，不按票数或角色权威决定。
5. **交付与状态**：给出图文汇报、完整证据记录和下一步。主理裁决是审稿建议；作者未采纳的内容不写成已确认设定。结论可为“本轮范围未见重大问题”，不等于整剧通过或制作完成。

只审稿时在此结束。不要把“采纳某条审稿建议”自动理解成获准改写全部剧本。

## 5. 改稿和定向复核

用户要求改稿时，在原稿之外另存候选版。按修改目标组织任务：关联争议 ID、影响场次／人物／伏笔、需保留项、最小改法、完成标准；替代方案之间的取舍不可推断时交由作者决定。

复核读取候选新稿与原稿差异，逐条确认问题是否解决、是否损伤原有亮点或引入新问题。人物、规则或伏笔变更检查后续消费者：只标记受影响的分集、卡片、分镜或镜头需复核。记录“已解决／部分解决／未解决／撤回”与新版本依据；没有实际改稿就不能填“已复核通过”。

续做保存原稿版本、各席意见、争议与裁决、作者选择、候选改稿、复核结果。作品与审稿记录放创作目录，不写进 Skill 包。

## 6. 面向作者的图文汇报

默认使用 [Markdown 图文模板](../assets/script-review-template.md) 的“主理汇报”部分。给作者的报告先讲结论和最值得保留的设计，再展示关键问题；完整各席过程留在记录中，不让作者先读代理流水账。

每个关键争议配一个最能解释它的图，尽量只画相关场次：因果缺口用因果链，人物动机用选择链／关系图，节奏问题用信息与情绪节拍。图中节点标场号／段落；原稿直接事实、推断和修改建议用文字及样式共同区分，不仅靠颜色。没有明确问题时展示成立的叙事链，不虚构漏洞。

图后紧接短原文、正反理由、主理判断、最小修改方案及代价、验收方式。原稿事实与建议分开展示，禁止把建议画成已经发生的情节。工具不能显示图时，降级为带箭头的文本图／表格，并说明展示限制；不把静态图称为已验证的交互网页。

### 可打开的交互网页

用户要求网页、可打开图文报告或原稿／建议切换时，复制 [HTML 汇报模板](../assets/script-review-report.html) 到创作目录，填充其中 `review-data` JSON；页面不依赖第三方库或外部服务。不要改安装目录里的模板来保存作品。

数据约定（模板内有同名字段）：

- 顶层：`title`、`version`、`scope`、`mode`（实际评审方式）、`status`、`conclusion`、`strengths`（文字数组）、`questions`（待决定项数组）、`issues`。
- 每个 issue：`id`、`title`、`location`、`kind`（判断类型）、`impact`、`evidence`（短原文）、`positive`、`negative`、`character`、`audience`、`decision`、`reason`、`uncertainty`、`task`、`acceptance`、`original`、`proposal`。
- `original`／`proposal` 各含 `caption`、`nodes`。每个 node 为 `{ "text": "节点文字", "source": "场号／段落", "type": "fact 或 inference 或 proposal 或 gap" }`；节点顺序表示因果／选择／节拍的阅读顺序，建议每链 2—6 个。复杂分支关系改用 Markdown Mermaid 或为该争议专画图，不硬塞进线性链。`proposal` 缺省表示尚无修改方案；UI 应如实显示。

渲染后核对引文、图示与版本，再在可用浏览器检查争议选择、原稿／建议切换、窄屏和键盘操作。若未做浏览器检查，保留“交互／视觉未验证”的限制。模板空态、演示填充、真实剧本试审、作者验收分别记录。

## 开始与测试

用户提供稿件即可开始；可附重点和锁定项，不要求先做人物图或生成视频。

```text
$dear-deer-drama-workbench 对附件第一集做一轮正反方剧本讨论，五个角色都参与。
重点检查人物动机与剧情因果。保留原稿，先讨论不改稿，给我图文主理汇报。
```

想测试独立评审时可加“在当前宿主允许的情况下使用独立评审代理，如不可用请说明实际模式”。想要网页可加“给可打开的交互图文报告”。

试审验收看：五席是否按实际模式执行；引用能否定位；正反是否回应对方最强依据；主理是否给出有理由的裁决；事实与建议是否分开；任务是否能指导改稿；未验证项是否如实保留。文件与链接检查通过仅证明能力包可加载，真实剧本试审和作者验收另记。
